# UI audit — 2026-10-03

Scope: Android companion UI in the `goby` worktree. Requested direction:
Liquid Glass, adapted to the existing Kotlin/XML Android implementation.

## Findings and changes

| Finding | Change |
| --- | --- |
| Much of the explanatory text was 10.5–12sp. | Supporting copy is 14sp, fields 16sp, and section headings 16sp. |
| Two-column notification switches squeezed long labels. | Full-width, 56dp switch rows. |
| 44dp device buttons shared a row with long device names. | Device details wrap above a full-width, 52dp button. |
| Fixed button heights could clip larger system text. | Wrap-content buttons with minimum heights and vertical padding. |
| Flat white surfaces did not match the requested material. | Native translucent gradients, layered borders, and floating navigation in both themes. |
| Diagnostic tools appeared before daily activity. | Activity appears after filters; secondary diagnostics expand on demand. |
| Permission troubleshooting occupied the settings page. | Expandable help keeps the Bluetooth section easier to reach. |
| Badges competed with headings on narrow screens. | Permission and connection badges sit below the associated heading. |
| White button labels were assumed in every theme/state. | Semantic foreground tokens and disabled color selectors. |
| Tab motion ignored the animation setting. | System animation-scale checks before tab transitions. |
| Expanded panels could reset when the activity is recreated. | Store panel state and selected tab in the activity bundle. |
| Decorative icons repeated nearby accessible labels. | Decorative images are removed from accessibility traversal. |

## Design process

Used `ui-ux-pro-max` and `anti-ai-slop-design`. The legacy `antislop` skill
names in `AGENTS.md` were searched for but were unavailable; the installed
design skill supplied the applicable craft checks. The user was asked about
review timing; review was performed during implementation while that optional
preference was pending.

The broad design-system search returned an unrelated restaurant/landing-page
recommendation, which was discarded. The explicit Liquid Glass style search
was relevant; its platform constraint informed the native Android material
adaptation. Android and Material Components documentation was fetched using
Context7 before implementation.

## Verification

- All resource XML files parse.
- Composited normal-text colors exceed 4.5:1 across the checked canvas and glass
  endpoints in light and dark mode. Status badge text pairs also exceed 4.5:1.
- `gradlew.bat assembleDebug lintDebug` completed successfully with the project's
  normal dependencies and settings. Lint reports one existing fatal finding
  (`ExpiredTargetSdkVersion`, target SDK 32) and 60 warnings; the build currently
  has `abortOnError false`. This is not a clean lint result. Updating the target
  SDK requires a separate compatibility review of Bluetooth and background
  notification behavior.
- Four isolated Robolectric 4.16.1 checks pass using native Android graphics on
  API 28: light/dark portrait layouts, 320dp large text at 2x scale and landscape,
  preserved diagnostic controls and long device names, and expansion/tab state
  after activity recreation with animations disabled. Rendered clickable targets
  checked by the harness are at least 48dp high.
- Native renders at 375x812, 320x640, 812x375, and 800x1280 were inspected. The
  expanded navigation form reaches the end of the scroll area above the floating
  bar. A gradient scrim keeps underlying text from competing with navigation.
- The existing manifest locks the application to portrait. Landscape checks
  exercise the layout renderer; they do not claim that landscape is enabled in
  the shipped app.
- Fixed the Windows Gradle wrapper's unconditional failure return after a
  successful build; successful builds now return exit code 0.
- `git diff --check` passes. No production dependencies were added.

APK: `app/build/outputs/apk/debug/ESP32-SmartNotif-LiquidGlass.apk`.
Native render previews: `app/build/ui-review/` (generated artifacts).

The native rendering harness is isolated outside the repository and does not
add production dependencies. A native render is not a physical-device test.
BLE delivery, system permission screens, TalkBack operation, keyboard behavior,
and hardware-specific system insets require additional device verification.
